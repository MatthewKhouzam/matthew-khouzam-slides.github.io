MCP Doesn't Scale and Anthropic Just Admitted It...

  • Report this article
Rob Murphy

Rob Murphy

Published Dec 1, 2025
+ Follow

It is almost heresy to question something with so much momentum but take a deep breath and keep an open mind; MCP might not be right for the "use it everywhere for everything!!" moment it is having...

MCP is absolutely everywhere. Model Context Protocol servers are being embraced across a wide array of use cases, some that truly work and some that simply won't. Why the fits mixed in with the misses? We're still early in our collective AI journey. The immaturity of our exposure to using AI and in this context, MCP, means we don't have intuition around when and where many parts of AI work just yet.

Why this article today? Better intuition? Definitely not. I hit the MCP gaps earlier than most as over the last months I spent time pushing MCP servers from various projects and vendors to their limits, looking for where the edges became clear. Through that process, I developed a good feel through real observations about that fit. “Maybe not for that latency sensitive use case” or “user facing production agents might not be an MCP strength” was shared with colleagues and customers more than a few times. But honestly? It felt like crying wolf. MCP has tremendous momentum, and experiences with it in coding agents like Claude Code are genuinely excellent.

What I knew was that low-latency, low inference cost use cases where model selection matters would be a tough fit for most MCP servers. The architecture didn't align with those requirements.

Not everyone bought my line of thinking. I understand why. MCP represents one of the first real interoperability stories in agentic AI.

Then last week, Anthropic published their blog post on "Code execution with MCP: building more efficient AI agents." Anthropic, the creators of MCP, quietly admitted that MCP might have some issues...

Their "optimization guidance" essentially admits MCP doesn't scale for most production use cases. Companies are rushing to adopt MCP just as Anthropic quietly explains how to work around its fundamental limitations.

What is MCP (And Why It Matters)

The Model Context Protocol was introduced by Anthropic just a year ago, in November 2024, as an open standard for connecting AI agents to external systems. The core promise: instead of building custom integrations for every agent-tool pairing, implement MCP once and unlock an entire ecosystem.

This is genuinely valuable. The MCP protocol makes integration points possible in ways that were cumbersome before.

But MCP's success wasn't guaranteed. It wasn't until Google backed it at Google Next in April 2025 that it became the de facto standard. That validation triggered rapid adoption. Thousands of MCP servers emerged, and suddenly everyone was building with MCP.

The challenge? That momentum happened faster than our understanding of where MCP actually fits. Companies saw the integration benefits and assumed it belonged everywhere.

The Critical Distinction

There are two very different types of agents, and MCP's fit varies dramatically between them.

  • Coding agents like Claude Code and OpenAI Codex handle complex, exploratory tasks requiring deep reasoning. They need access to many possible tools and understand sophisticated schemas. When you're doing exploratory work and development, MCP's overhead is justified. You're optimizing for capability, not speed. I have to bundle "desktop" agents like Claude Desktop here as the models behind it are frontier and MCP integration, like with coding agents, is excellent.
  • Organizational agents are different. Customer service automation, task routing, and data updates need to be lightweight, fast, and cost-effective at scale. They're latency-sensitive components in dynamic agentic networks where MCP is a tough to impossible fit. Most enterprises building AI systems are creating this second type.

When you're building production agents that need to respond in milliseconds and run thousands of times per day, MCP's architecture becomes a fundamental mismatch.

What Anthropic's Blog Really Says

Anthropic's recent blog post is masterfully diplomatic. It's framed as optimization guidance. But read between the lines and you'll see a course correction.

Their solution? Don't actually use MCP as designed. Instead, generate a filesystem structure where each tool becomes a code file, have agents discover tools by browsing directories, and write code that calls APIs.

They're proposing you reduce token usage from 150,000 to 2,000, a 98.7% reduction, by essentially not using MCP's direct tool-calling approach. You're back to calling APIs with code, which is what we did before MCP existed.

Even more telling? Anthropic support has been advising users to "drop MCP connections to buy more conversational tokens." This is not reddit chatter, I had this conversation with a very apologetic Anthropic Support Engineer; they had a defect in chat length calculation and the immediate advice was to disable MCP servers that were not needed.  Buy back some token space while they fixed the defect.

For coding agents with code execution environments, this works well. But for latency-sensitive production agents? This blog post highlights exactly why MCP doesn't fit.

The Token Economics & Latency Problem

In real-world testing with Couchbase MCP, the contrast was stark. For agentic coding, it works amazingly well, like a secret unlock that makes everything easier. But in an agentic network, converting natural language to SQL required context about collections and relationships that landed near 20,000 tokens. Add in the tokens that the MCP definitions required, LLM latency to sort through everything and you had a challenge. The same task via a clean REST endpoint? Around 1,000 tokens and performance was excellent..

The goal was to use a Small Language Model, and MCP became a real challenge. That's a 20x token difference. Small Language Models just can’t handle so much context and with fewer attention heads, wading through it all to understand where to focus is almost an anti-pattern.

The latency impact compounds this. More tokens mean longer processing. In dynamic agentic networks, MCP's overhead kills responsiveness.

At scale, you're paying for infrastructure overhead instead of AI reasoning. Your architectural choice forces expensive model choices. Organizations end up needing and using bigger, trillion parameter models like Gemini, Opus 4 (and now 4.5!) and GPT-5, not for the actual task, but to parse through the tool bloat.

You can't use smaller, faster models because the protocol overhead requires frontier-level reasoning. Your architecture has trapped you into expensive infrastructure choices.

The Open Source Opportunity Cost

MCP's token bloat pushes everyone toward frontier models and away from the open source ecosystem.

Well-tuned smaller models like NVIDIA's Nemotron 70B work beautifully with clean tool definitions. I've run Nemotron Nano 9B-v2 on a 64GB memory edge GPU device doing tool calling through a simple REST API. Setup time? Twenty minutes. Performance? Excellent.

Try the same setup with MCP and you'd flood the box, it is the definition of technical overkill.

The right architecture should be heterogeneous: big models for customer-facing reasoning, small efficient models for background tool calling. MCP challenges approach this by forcing every agent to carry the same protocol burden.

The result? Companies will have to over-engineer their infrastructure. Necessity will drive the need to deploy expensive cloud inference for tasks that could run perfectly on local hardware. They miss the opportunity for cost-effective deployment of open source models.

When MCP Actually Works

MCP has legitimate use cases where it excels.

Coding agents doing complex database exploration justify the overhead. When you're doing exploratory development with potentially hundreds of tools, MCP's integration benefits outweigh the token costs.

The MCP protocol genuinely makes these integration points easier. That value is real.

But lightweight production agents doing routine automation? No. Latency-sensitive agentic networks? Definitely not. Customer service bots with a dozen simple tools? You're burning money.

The decision tree is straightforward: if your use case involves exploration, complexity, and tolerance for latency, MCP might fit. If you need efficiency, speed, and scale with predictable operations, you want simpler tooling.

The Path Forward

For decision makers: your architectural choices determine both your model costs and your latency profile. Don't assume MCP belongs everywhere. Assess your actual needs. Are you building exploratory coding tools or production automation?

For technical teams: use simple REST endpoints for most organizational agents. Reserve MCP for coding agents and complex exploratory work. Stop passing tool definitions repeatedly. Match both your model size and your protocol choice to actual task requirements.

This isn't about abandoning MCP. It's about using it strategically.

The industry is still immature. We're figuring out these patterns in real-time, but that means you shouldn't lock into expensive architectural patterns based on incomplete understanding.

Reading Anthropic's blog post validated concerns that felt lonely to voice. The limitations are real. The scaling challenges are fundamental.

Build for the agents you actually need, not the ones that demo well. Understand the distinction between coding agents and production agents. Choose your tooling based on your requirements, not on what's trending.

MCP is a valuable tool. Let's use it like one: deliberately, strategically, where it fits. Not everywhere.
