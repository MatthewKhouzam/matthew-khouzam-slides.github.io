MCP 2026-07-28

Stateless, Streamable & How We Uplifted

Matthew Khouzam | Ericsson Research | August 2026

This deck covers the MCP spec update released July 28 2026, what changed from the previous 2025-03-26 spec, and how we uplifted two real projects: TMLL (Python harness) and Theia (TypeScript IDE plugin).
Matthew Khouzam · Ericsson Research · August 2026

The Problem with 2025-03-26

Why the spec needed to change

The original MCP spec was designed for local IDE use cases. It broke down at scale.

Session State Pain

  • Long-lived sessions server accumulates per-client state
  • Sticky sessions SSE requires load-balancer affinity
  • Orphaned state client drops = no cleanup path
  • No horizontal scaling session pinned to one instance
If a client disconnected, the server had no standard way to know whether to keep or discard state. This made serverless and CDN deployments impossible.

Transport Limitations

  • SSE required two connections: GET (stream) + POST (requests)
  • Not supported by many corporate proxies
  • No request-response correlation built-in
  • stdio only fine for local, useless for remote

SSE was a workaround, not a design choice. It leaked complexity into every deployment.

SSE was the only remote transport option, and it was problematic in enterprise networks with proxies that terminate long-lived connections.

What's New in 2026-07-28

The headline changes

This is the biggest MCP spec revision since launch. It fundamentally changes the transport and session model.

🏗️ Stateless by Default

  • No session IDs required each request is self-describing
  • Server MAY opt into sessions (not MUST)
  • Mcp-Session-Id header only if server chooses to issue one
  • Enables serverless, CDN, and horizontal scaling

Stateless servers are now first-class citizens, not an afterthought.

This is the single biggest change. Servers no longer need to track clients. A simple tool server can be a plain HTTP endpoint with zero state.

🔀 Streamable HTTP

  • Replaces SSE as the remote transport
  • Single endpoint POST for requests, optional SSE response body
  • Request-response OR streaming server decides per-call
  • Standard HTTP semantics works with proxies, CDNs, load balancers
Streamable HTTP is elegant: you POST a JSON-RPC request, and the server either returns a JSON response immediately or opens an SSE stream in the response body. Same endpoint, same method.

🔐 OAuth 2.1 & Security

  • Mandatory for remote HTTP servers
  • PKCE required no client secrets in public clients
  • Dynamic client registration supported
  • Resource indicators for token scoping
  • Metadata discovery via /.well-known/oauth-authorization-server
OAuth 2.1 with PKCE is now the standard auth flow. This replaces the ad-hoc bearer token approaches people were using.

🏷️ Tool Annotations

  • readOnlyHint tool only reads, never mutates
  • destructiveHint tool may delete or modify irreversibly
  • idempotentHint safe to retry
  • openWorldHint interacts with external systems

Annotations are hints, not guarantees but they enable smarter client UX (auto-approve read-only tools)

Clients can use these to auto-approve safe operations, show warning dialogs for destructive ones, or batch idempotent calls.

📦 More New Features

  • Structured output outputSchema on tools for typed responses
  • Elicitation server prompts user for input mid-tool
  • MCP Apps text/html;profile=mcp-app for rich UI
  • JSON-RPC batching multiple requests per HTTP call
  • Resource links tools can return links to resources
Structured output is huge for agentic workflows the LLM can reliably parse tool results. Elicitation lets a tool ask the user a question without aborting. MCP Apps enable inline UIs in chat.

Transport Deep-Dive

From SSE to Streamable HTTP

Let's look at exactly how the transport model changed.

Before vs After

Aspect2025-03-26 (Old)2026-07-28 (New)
Remote transportSSE (GET+POST pair)Streamable HTTP (single POST)
SessionRequired (server-managed)Optional (server MAY issue)
Local transportstdiostdio (unchanged)
Response modeAlways streamingJSON or SSE (per-request)
Endpoints/sse (GET) + /messages (POST)/mcp (POST only)
ConnectionLong-livedPer-request
The key insight: Streamable HTTP is just normal HTTP POST. The server can choose to return a plain JSON response OR upgrade the response body to an SSE stream for long-running operations. Same endpoint either way.

Streamable HTTP Request Flow

Simple tool call (fire-and-forget):

Client → POST /mcp (JSON-RPC request)
Server → 200 OK + JSON-RPC response body

Long-running tool (streaming):

Client → POST /mcp (JSON-RPC request)
Server → 200 OK + Content-Type: text/event-stream
Server → SSE events (progress, partial results)
Server → final JSON-RPC result event + close

This is the elegance of the design. Simple tools get simple HTTP semantics. Complex tools get streaming. The client doesn't need to know in advance which it'll get.

Session ID Now Optional

  • Server MAY return Mcp-Session-Id in initialize response
  • If present, client MUST include it in subsequent requests
  • If absent → fully stateless
  • Server can DELETE /mcp to terminate session
// Stateless server  no session header
POST /mcp HTTP/1.1
Content-Type: application/json

{"jsonrpc":"2.0","method":"tools/call","params":{...},"id":1}
Most simple tool servers will be stateless. Session IDs are only needed for servers that maintain subscriptions or long-running state across requests.

Case Study: TMLL

Python harness-level uplift

TMLL is a trace analysis MCP server. It's a good example of a simple, tool-heavy server that needed minimal changes to comply with 2026-07-28.

TMLL Before & After

Before (SDK 1.27.0)

from mcp.server.fastmcp import FastMCP
from mcp.server.fastmcp import Image

mcp = FastMCP("tmll-cli-mcp-server")

After (SDK 2.0.0)

from mcp.server import MCPServer
from mcp.server.mcpserver import Image

mcp = MCPServer("tmll-cli-mcp-server")

Core change: FastMCP → MCPServer class rename. API surface identical.

The Python SDK 2.0 renamed the high-level class from FastMCP to MCPServer. The decorator-based API (@mcp.tool, @mcp.resource) is unchanged.

TMLL What Changed

  • Import paths mcp.server.fastmcp → mcp.server / mcp.server.mcpserver
  • Monkey-patching removed no more _mcp_server internal access
  • ToolAnnotations added for safety hints
  • Transport unchanged stdio stays as-is
  • Tool registration unchanged @mcp.tool() decorators work the same
The uplift took one commit. Most of the work was search-and-replace on import paths. The ToolAnnotations addition was optional but good practice.

TMLL Tool Annotations

from mcp.types import ToolAnnotations

@mcp.tool(annotations=ToolAnnotations(
    readOnlyHint=True,
    destructiveHint=False,
    openWorldHint=False
))
async def list_experiments() -> str:
    """List all open experiments."""
    return await run_cli(["list-experiments"])

@mcp.tool(annotations=ToolAnnotations(
    readOnlyHint=True,
    destructiveHint=False,
    openWorldHint=True
))
async def detect_anomalies(...) -> str:
    """Run anomaly detection on trace data."""
    ...
14 tools, most marked readOnly. Only delete_experiment and ensure_server are destructive. detect_anomalies is openWorld because it contacts the trace server.

TMLL Complexity Assessment

Uplift complexity: LOW

  • ✅ Import renames (mechanical)
  • ✅ Remove monkey-patching (simplification)
  • ✅ Add ToolAnnotations (optional, additive)
  • ✅ No transport changes (stdio unchanged in spec)
  • ✅ No session logic to remove (was already stateless)

Total: 1 commit, ~20 lines changed

If your server is stdio-only and stateless, the uplift is trivial. It's essentially a dependency bump plus import renames.

Case Study: Theia

TypeScript plugin-level uplift

Theia is a full IDE with both MCP client and server. The uplift was significantly more complex it touched transport, session management, OAuth, and the plugin API.

Theia Architecture

MCP Client
Connect TO external servers
  • StreamableHTTP (primary)
  • SSE (fallback)
  • stdio (local)
  • OAuth 2.1 + PKCE
MCP Server
Expose Theia AS a server
  • Stateless StreamableHTTP
  • Single /mcp endpoint
  • Per-request transport
  • Tools + Resources + Prompts
Theia has both sides: it connects to external MCP servers (client) AND exposes itself as an MCP server for external AI tools to use. Both needed uplifting.

Theia Server Stateless Uplift

Before

// Session-tracking transport
const transport =
  new StreamableHTTPServerTransport({
    sessionIdGenerator: () =>
      randomUUID(),
  });
// Map of active sessions
httpTransports.set(
  sessionId, transport
);

After (2026-07-28)

// Stateless  no session tracking
const transport =
  new StreamableHTTPServerTransport({
    sessionIdGenerator: undefined,
  });
// Per-request, no map needed
// Transport created and disposed
// within request handler
The key change: sessionIdGenerator is set to undefined, which tells the SDK to not generate or expect session IDs. Each request gets its own transport instance that's cleaned up when the response closes.

Theia Client Transport Negotiation

async doStart(): Promise<void> {
  try {
    // Try Streamable HTTP first (2026-07-28)
    this.transport = new StreamableHTTPClientTransport(
      url, { authProvider: this.oauthProvider }
    );
    await this.client.connect(this.transport);
  } catch (e) {
    // Fall back to SSE for legacy servers
    this.transport = new SSEClientTransport(
      url, { authProvider: this.oauthProvider }
    );
    await this.client.connect(this.transport);
  }
}

Graceful degradation: StreamableHTTP → SSE fallback → stdio for local

Theia's client is backwards-compatible. It tries the new transport first and falls back to SSE for servers that haven't upgraded yet.

Theia OAuth 2.1 Stack

  • MCPOAuthClientProvider tokens, PKCE, dynamic registration
  • Credential store keyed by server name + URL
  • Callback service handles OAuth redirects
  • Interactive mode launches browser for consent
  • Non-interactive mode autostart with stored tokens

+8,190 lines for the full OAuth stack

OAuth is the biggest single addition. It required a credential store, callback handlers for both browser and Electron, token refresh logic, and integration with the server lifecycle.

Theia Plugin API

// Plugin authors register MCP server definitions
vscode.lm.registerMcpServerDefinitionProvider('my-tools', {
  provideMcpServerDefinitions(): McpServerDefinition[] {
    return [{
      type: 'http',
      name: 'My Remote Server',
      url: 'https://my-server.com/mcp',
      // OAuth handled automatically by Theia
    }];
  }
});

Supports McpStdioServerDefinition and McpHttpServerDefinition

Theia plugins can register MCP server definitions declaratively. The IDE handles transport negotiation, auth, and lifecycle.

Theia Complexity Assessment

Uplift complexity: HIGH

  • ✅ Stateless server transport (moderate remove session map)
  • ✅ StreamableHTTP client + SSE fallback (moderate)
  • ⚠️ OAuth 2.1 full stack (high +8K lines)
  • ✅ Plugin API types for HTTP servers (low)
  • ✅ SDK bump to 1.30.0 (low)

Total: multiple PRs, ~10K lines changed

The OAuth stack dominates the effort. If you only need stateless transport, the uplift is moderate. Full OAuth for remote servers is where the complexity lives.

Migration Checklist

What you need to do

Here's the practical checklist for uplifting your MCP server or client to 2026-07-28.

Server-Side Checklist

  • ✅ Bump SDK Python: mcp>=2.0.0 · TS: @modelcontextprotocol/sdk@^1.30.0
  • ✅ Replace SSE with Streamable HTTP transport (if remote)
  • ✅ Remove session tracking set sessionIdGenerator: undefined
  • ✅ Add ToolAnnotations readOnly, destructive, idempotent hints
  • ✅ Add outputSchema to tools returning structured data
  • ⚠️ Implement OAuth 2.1 if server is exposed remotely
Items 1-5 are straightforward. OAuth is the only high-effort item and only needed for remote servers.

Client-Side Checklist

  • ✅ StreamableHTTP transport as primary
  • ✅ SSE fallback for legacy servers
  • ✅ Handle optional session ID include if server provides one
  • ✅ OAuth 2.1 client PKCE, token refresh, credential store
  • ✅ Handle structured output parse outputSchema from tools/list
  • ✅ Support elicitation respond to server prompts for user input
Clients have more work because they need to handle both old and new servers. The fallback pattern from Theia is a good reference.

Testing & Validation

  • 🧪 MCP Inspector interactive testing tool
  • 🧪 Verify initialize handshake with no session header
  • 🧪 Test both JSON response and SSE streaming modes
  • 🧪 Validate ToolAnnotations appear in tools/list
  • 🧪 OAuth flow: authorization, token refresh, token expiry

npx @modelcontextprotocol/inspector test your server interactively

The MCP Inspector is invaluable. It lets you connect to your server, list tools, call them, and see the raw JSON-RPC traffic.

Key Takeaways

What this means for us

Summary of actionable insights.

The Big Picture

  • Stateless = simpler servers easier horizontal scaling, serverless-friendly
  • Streamable HTTP = modern HTTP CDN-friendly, proxy-safe, standard semantics
  • OAuth 2.1 = production security required for remote, enterprise-grade
  • The spec rewards read-only, annotation-rich tool design
  • stdio stays unchanged simplest path for local tools
The protocol is maturing rapidly. The stateless-by-default stance is a clear signal that MCP is targeting production deployments, not just local IDE integrations.

Recommendations

  • 📌 Start with annotations low effort, high value for clients
  • 📌 Design stateless-first avoid server-side session state
  • 📌 Use outputSchema enables reliable agentic workflows
  • 📌 Plan for OAuth if deploying remote servers
  • 📌 Test with Inspector before claiming compliance
If you do nothing else, add ToolAnnotations and outputSchema. These are additive, non-breaking, and immediately useful to clients.
