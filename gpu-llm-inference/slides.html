Part 1: Foundations

What is a GPU, how do LLMs work, and why does memory bandwidth matter?

Starting with the fundamentals before we get into hardware specifics.

What is a GPU?

CPU: Few powerful cores

  • 4-128 cores
  • Complex control logic
  • Branch prediction, OOO execution
  • Optimized for latency

GPU: Many simple cores

  • Thousands of cores
  • Minimal control logic
  • SIMT execution model
  • Optimized for throughput
CPU: sports car for one person. GPU: bus carrying 10,000 passengers. Different tools for different jobs.

SIMT: Single Instruction, Multiple Threads

  • Threads grouped into warps (NVIDIA, 32 threads) or wavefronts (AMD, 64 threads)
  • All threads in a warp execute the same instruction simultaneously
  • Divergent branches cause serialization (both paths execute, inactive threads masked)
  • Thousands of warps in-flight hide memory latency through occupancy
GPUs achieve high throughput by trading single-thread performance for massive parallelism.
This is why GPUs excel at matrix operations - every element can be computed independently in parallel.

How Large Language Models Work

  • Transformer architecture - attention mechanism processes all tokens in context
  • Parameters - billions of learned weights (1B to 405B+)
  • Inference - two phases:
    • Prefill: process entire prompt in parallel (compute-bound)
    • Decode: generate tokens one-by-one (memory-bound)
  • Each token generation reads all model weights from memory
The key insight: during decode, we read the entire model from memory for each single token. This is why bandwidth dominates performance.

Why LLM Inference is Computationally Brutal

  • Each transformer layer performs massive matrix multiplications
  • Every input token must be multiplied against every weight in each layer
  • A 7B model has ~32 layers, each with multiple weight matrices (Q, K, V, O, FFN up, FFN down)
  • For a single token: ~14 billion multiply-add operations (2x params)
  • Attention: every token attends to every other token in context (O(n^2) with sequence length)
Generating one token from a 70B model requires ~140 billion multiply-add operations. At 1000 tok/s, that's 140 TFLOPS sustained - and every operation needs its weight read from memory.
This is not a simple convolution but a dense matrix-vector product: every output element depends on every input element multiplied by a unique weight. No shortcuts, no sparsity (unless you add it artificially). The weight matrix IS the model's knowledge.

The Core Operation: Matrix-Vector Multiply

Per Layer (simplified)

// For each of ~32 layers:
output = W_q @ input    // Query projection
output = W_k @ input    // Key projection
output = W_v @ input    // Value projection
attn = softmax(Q @ K^T) // Attention scores
output = attn @ V       // Weighted values
output = W_o @ output   // Output projection
hidden = W_up @ output  // FFN expand (4x)
output = W_down @ hidden // FFN compress

Each @ is a full matrix multiply - every element touches every weight.

Why this is hard

  • Matrix-vector multiply: O(n x m) operations
  • No element can be skipped - unlike convolutions with local receptive fields
  • FFN layers expand 4x then compress: 4096 to 16384 to 4096
  • Every weight used exactly once per token (no reuse)
  • This is why memory bandwidth, not compute, is the bottleneck
In a CNN, each filter is small and reused across the image (data reuse). In an LLM, each weight is massive and used once per token (no reuse). This fundamental difference is why LLMs are memory-bound during decode.

Animated: One Token Decode Step

The purple dashed lines represent weight reads from HBM - this is the bottleneck. Every layer must read its entire weight matrix for each token.

Watch the data flow: token enters, gets embedded, passes through every transformer layer (each reading its weights from HBM), through the LM head, softmax, and out comes one new token. Then the whole thing repeats. The weight reads are 99% of the time.

Animated: How Agentic AI Works

The LLM is the reasoning engine at the center. A harness orchestrates the loop: prompt → reason → act (tool call) → observe (feedback) → repeat until the goal is achieved.

Agentic AI puts the LLM in a loop. Instead of a single prompt-response, the harness keeps calling the LLM, letting it invoke tools (search, code execution, file I/O, APIs), then feeding the results back as context. The loop continues until the task is complete. This is how modern coding assistants, research agents, and autonomous workflows operate.

Why Memory Bandwidth is Everything

  • LLM decode is memory-bandwidth bound, not compute-bound
  • Modern GPUs have hundreds of TFLOPS of compute but are starved for data
  • Examples of the compute-vs-bandwidth mismatch:
    • H100: 3958 TFLOPS FP8, but only 3.35 TB/s BW (1181:1 ratio)
    • MI300X: 2614 TFLOPS FP8, but only 5.3 TB/s BW (493:1 ratio)
    • Gaudi 3: ~1835 TFLOPS FP8, but only 3.7 TB/s BW (496:1 ratio)
  • LLM decode: ~2 ops per byte read (one multiply-add per weight)
LLM decode has arithmetic intensity of ~1 op/byte. GPUs need ~500-1000 ops/byte to be compute-bound. Every vendor hits this same wall.
This is why a 4090 with 1/5th the compute of H100 can run LLMs at competitive speeds, and why MI300X's higher bandwidth compensates for lower compute vs H100.

The Memory Hierarchy

Registers: 20 TB/s, ~KB per SM
L1 / Shared Memory (SRAM): 10-20 TB/s, 128-256 KB per SM
L2 Cache (SRAM): 5-12 TB/s, 6-96 MB total
HBM / GDDR (DRAM): 0.5-8 TB/s, 16-192 GB
System RAM / NVLink / PCIe: 32-900 GB/s, TB scale

Bandwidth decreases, capacity increases. LLM weights live in HBM/GDDR.

The hierarchy is the fundamental tradeoff: fast and small vs slow and big. LLM weights are too large for on-chip SRAM, so we're bound by HBM bandwidth.

Batched serving (vLLM, TensorRT-LLM) can push toward compute-bound by amortizing weight reads across multiple requests. Single-user local inference is always bandwidth-bound.

Part 2: The Software Stack

CUDA, ROCm, SYCL, Vulkan - and how LLM frameworks use them

The software layer determines what hardware you can target and what optimizations are available.

NVIDIA CUDA

  • Released 2007 - first-mover advantage, dominant ecosystem
  • Proprietary compiler (nvcc), runtime, driver stack
  • Key libraries: cuBLAS (linear algebra), cuDNN (deep learning), TensorRT (inference)
  • PTX intermediate representation allows forward compatibility
  • Tensor Core programming via WMMA/mma intrinsics
Nearly all LLM frameworks support CUDA first. The ecosystem moat is enormous.
CUDA's real advantage isn't the language - it's the 15+ years of optimized libraries, tools (nsight), and community knowledge.

AMD ROCm

  • Open-source GPU compute platform (since 2016)
  • HIP: CUDA-like API that compiles for both AMD and NVIDIA
  • hipBLAS, MIOpen (cuDNN equivalent), rocBLAS
  • HIPIFY tool auto-converts CUDA source to HIP
  • Linux-first, limited Windows support historically
  • ROCm 6.x: significant stability improvements, MI300X focus
ROCm has narrowed the gap significantly. PyTorch and llama.cpp have good ROCm support.
The MI300X's 192GB HBM3 makes ROCm worth dealing with for large models. Software maturity is the main concern vs CUDA.

SYCL / Intel oneAPI

  • Khronos standard - single-source C++ for heterogeneous compute
  • Intel's oneAPI/DPC++ compiler: targets Intel, NVIDIA, and AMD GPUs
  • oneMKL, oneDNN - optimized math/DNN libraries
  • Advantage: write once, run on any GPU vendor
  • Used in Intel Gaudi accelerators and Arc GPUs
  • Ecosystem still smaller than CUDA or ROCm
SYCL is the ISO C++ approach to GPU programming - standard, portable, but less battle-tested for LLMs.
SYCL's promise of vendor portability is compelling, but in practice most LLM stacks still have vendor-specific code paths for peak performance.

Vulkan Compute

  • Khronos graphics/compute API - runs on everything (mobile, desktop, embedded)
  • SPIR-V shader/compute intermediate language
  • Used by llama.cpp for broad hardware support (Qualcomm, Mali, Intel, AMD, NVIDIA)
  • Lower overhead than OpenCL, more explicit control
  • No vendor-specific tensor core access (general SIMD only)
Vulkan trades peak performance for universality. Great for edge/mobile LLM inference.
llama.cpp's Vulkan backend means you can run LLMs on basically any GPU made in the last 8 years, including phones.

Part 3: Memory Hardware

SRAM, DRAM, GDDR, HBM - the technologies that determine inference speed

Memory technology is the single biggest factor in LLM inference performance. Let's understand what's available and why.

SRAM - Static RAM

  • 6 transistors per bit - fast, no refresh needed, but enormous area cost
  • Used for: register files, L1/L2 cache, shared memory
  • Can be on-chip (registers, L1, shared memory) or off-chip (external SRAM, Cerebras wafer-scale)
  • Bandwidth: 10-80 TB/s aggregate across SMs (on-chip)
  • Capacity: KB (registers) to ~96 MB (L2 cache on B200); off-chip SRAM can be larger but slower
  • Latency: 1-20 cycles (on-chip), higher off-chip
SRAM is 100-1000x faster than DRAM but 100-1000x more expensive per bit. You cannot store an LLM in SRAM (yet) — though Cerebras' wafer-scale approach uses massive off-chip SRAM arrays.
The H100 has 50MB of L2 SRAM. A 7B Q4 model needs ~3.5GB. We're still 70x short of fitting even a small model on-chip. Cerebras tries a different approach with wafer-scale SRAM. Off-chip SRAM (like in networking equipment) trades the latency advantage for larger capacity.

DRAM - Dynamic RAM

  • 1 transistor + 1 capacitor per bit - dense, cheap, but needs periodic refresh
  • All GPU memory (GDDR, HBM) is fundamentally DRAM
  • Key metrics: bandwidth, capacity, latency, power
  • Bank structure: multiple banks enable parallel access
  • Row buffer: reading an open row is fast; opening a new row costs 30-50ns
DRAM bandwidth is the primary bottleneck for LLM inference. Every improvement helps directly.
The capacitor leaks charge, requiring refresh every 64ms. This is why it's 'dynamic'. SRAM holds state indefinitely while powered.

HBM: High Bandwidth Memory

  • 3D-stacked DRAM dies connected via through-silicon vias (TSVs)
  • Wide interface: 1024-bit per stack (vs 32-bit GDDR)
  • Multiple stacks placed on silicon interposer next to GPU die
  • Lower clock speed than GDDR, but extreme parallelism
  • Higher power efficiency (pJ/bit) due to short signal paths
HBM achieves massive bandwidth through width, not speed. 1024 bits wide at lower clock vs GDDR's 32 bits at higher clock.
HBM is manufactured by SK Hynix, Samsung, and Micron. It's expensive and supply-constrained, which is why data center GPUs cost 10-40x more than consumer cards.

From Volta to Blackwell, MI50 to MI400, Larrabee to Gaudi, Apple Silicon, and Chinese alternatives

Part 4a: NVIDIA

Volta to Blackwell — defining the AI accelerator

NVIDIA Volta (2017) - V100

  • First Tensor Cores - 4x4 FP16 matrix multiply-accumulate per cycle
  • 5120 CUDA cores, 640 Tensor Cores
  • HBM2: 16/32 GB, 900 GB/s bandwidth
  • 125 TFLOPS FP16 tensor, 15.7 TFLOPS FP32
  • 300W TDP, TSMC 12nm
Volta introduced tensor cores and defined the template for all AI accelerators that followed. The V100 was the workhorse of the first LLM training era (GPT-2, BERT).
The V100 is still found in many cloud instances. At 900 GB/s, a 7B Q4 model runs at ~130 tok/s theoretical. Many universities still train on V100 clusters.

NVIDIA Ampere (2020) - A100

  • 3rd-gen Tensor Cores - TF32, BF16, INT8, sparsity (2:4)
  • 6912 CUDA cores, 432 Tensor Cores
  • HBM2e: 40/80 GB, 2039 GB/s bandwidth
  • 312 TFLOPS BF16 tensor, 624 TFLOPS with sparsity
  • 400W TDP, TSMC 7nm
  • Multi-Instance GPU (MIG): partition into 7 isolated instances
The A100 80GB was the first GPU that could run a 70B model (FP16) without multi-GPU. The 2 TB/s bandwidth was a step-change.
Ampere introduced structured sparsity and BF16 support. The 80GB variant is still the price/performance sweet spot for many deployments.

NVIDIA Hopper (2022) - H100 / H200

H100

  • 4th-gen Tensor Cores + FP8
  • HBM3: 80 GB, 3.35 TB/s
  • 3958 TFLOPS FP8 tensor
  • Transformer Engine (dynamic FP8/FP16)
  • 700W TDP, TSMC 4nm

H200

  • Same GPU die as H100
  • HBM3e: 141 GB, 4.8 TB/s
  • 76% more memory, 43% more bandwidth
  • Fits 70B FP16 in single GPU
  • 700W TDP
Hopper's Transformer Engine automatically mixes FP8 and FP16 during computation for optimal accuracy/performance. The H200 is a memory refresh that makes large models practical on 1 GPU.

NVIDIA Blackwell (2024) - B100 / B200 / GB200

  • Dual-die design - two GPU chiplets connected via 10 TB/s NV-HBI
  • 5th-gen Tensor Cores, FP4 support
  • HBM3e/HBM4: up to 192 GB, 8 TB/s bandwidth
  • B200: 9 PFLOPS FP4, 4.5 PFLOPS FP8
  • 1000W TDP (B200), 2700W (GB200 NVL72 per tray)
  • GB200 NVL72: 72 GPUs connected via NVLink, 13.5 TB aggregate memory
Blackwell doubles everything: bandwidth, compute, memory. The B200's 8 TB/s means a 70B Q4 model at ~1100 tok/s theoretical.
The GB200 NVL72 is designed for trillion-parameter models. 72 GPUs with unified NVLink fabric can serve models that would otherwise need complex tensor parallelism.

Part 4b: AMD

MI50 to MI400 — challenging NVIDIA with bandwidth and capacity

AMD MI50 (2018) - First CDNA Precursor

  • Vega 20 architecture (GCN-based, pre-CDNA)

  • 300W TDP, TSMC 7nm
  • First AMD GPU with ROCm as primary compute platform
The MI50 proved AMD could compete in datacenter compute. It started the journey that led to the MI300X.
The MI50 was competitive with V100 on paper but ROCm software maturity was a significant gap. Many early adopters struggled with driver issues.

Part 4c: Intel

Larrabee legacy, Xe/Arc, and the Gaudi AI accelerator

Intel Larrabee (2008-2012) - The Road Not Taken

  • Concept: many x86 cores (32-80) with wide SIMD (512-bit)
  • Goal: programmable GPU using familiar x86 ISA
  • Cancelled as discrete GPU in 2010 - never shipped consumer product
  • Legacy: became Intel Xeon Phi (Knights Corner/Landing/Mill)
  • AVX-512 instruction set originated from Larrabee's vector units
Larrabee failed as a GPU because x86 overhead was too high for graphics. But its DNA lives on in AVX-512 and informed Intel's later GPU efforts.
Larrabee was ahead of its time conceptually - the idea of 'lots of simple programmable cores' is exactly what GPUs became. But the x86 tax was too heavy. Tim Sweeney called it 'the right idea, wrong execution'.

Intel Xe / Arc / Ponte Vecchio

Arc (Consumer, 2022)

  • Xe-HPG architecture
  • Arc A770: 16 GB GDDR6, 560 GB/s
  • XMX (matrix) engines
  • SYCL/oneAPI + limited CUDA compat

Ponte Vecchio (DC, 2022)

  • Xe-HPC architecture
  • 128 GB HBM2e, 3.3 TB/s
  • Aurora supercomputer GPU
  • 52 TFLOPS FP64

Arc Battlemage (2024): improved efficiency, better drivers, still limited AI ecosystem

Intel's GPU journey has been bumpy. Arc driver issues hurt adoption. Ponte Vecchio was late and expensive. But Intel keeps investing because they need a GPU story for AI.

Intel Gaudi - Dedicated AI Accelerator

  • Acquired from Habana Labs (2019) - purpose-built for AI training/inference
  • Not a GPU - uses Matrix Math Engine (MME) + Tensor Processing Cores (TPC)
  • Gaudi 2 (2022): 96 GB HBM2e, 2.45 TB/s, 24 TPCs
  • Gaudi 3 (2024): 128 GB HBM2e, 3.7 TB/s, improved MME
  • Integrated RDMA networking (no separate InfiniBand needed)
  • Intel discontinued Falcon Shores (Gaudi + Xe fusion) in 2025
Gaudi offers competitive price/performance for LLM inference but Intel's AI accelerator strategy has been volatile.
Gaudi 3 is competitive with H100 on LLM inference benchmarks at lower cost. But Intel's repeated strategy changes have scared away some customers.

Part 4d: Others & Apple Silicon

Chinese alternatives, Huawei Ascend, and Apple's unified memory approach

Moore Threads MTT S4000 (China)

  • Chinese GPU startup (founded 2020, MUSA architecture)
  • MTT S4000: 48 GB GDDR6, ~800 GB/s bandwidth estimated
  • Custom MUSA programming model (CUDA-like API)
  • Built on TSMC process (pre-export controls) and Samsung
  • Targets Chinese domestic market under US export restrictions
  • MUSIFY tool: CUDA-to-MUSA source translation
Chinese GPUs are 2-3 generations behind on hardware, but advancing rapidly. Export controls accelerated domestic development.
Moore Threads, along with Biren and Enflame, are building China's domestic GPU ecosystem. Performance is behind NVIDIA/AMD but they have a captive market of hundreds of millions of users.

Huawei Ascend / Atlas 350

  • Ascend 910C - Huawei's flagship AI processor (Da Vinci architecture)
  • Atlas 350 accelerator card: 1.56 PFLOPS FP4, 112 GB HBM
  • Claims 2.8x performance vs NVIDIA H20 (the export-legal NVIDIA chip)
  • CANN (Compute Architecture for Neural Networks) software stack
  • MindSpore framework integration, ONNX support
  • Manufactured on SMIC 7nm (N+2) process - no EUV
Huawei's Ascend is arguably the most advanced non-Western AI accelerator. The Atlas 350 targets H100 performance class.
Huawei's ability to build competitive AI chips on older process nodes (no EUV lithography) is impressive. They compensate with larger dies and architectural innovation. Baidu, Tencent, and Alibaba are deploying Ascend at scale.

Apple Silicon - Unified Memory Architecture

  • Unique approach: CPU, GPU, and Neural Engine share a single unified memory pool
  • No PCIe bottleneck - GPU reads directly from system DRAM (LPDDR5/5X)
  • M4 Max: 128 GB unified, 546 GB/s bandwidth, 40 GPU cores
  • M4 Ultra: 256 GB unified, ~819 GB/s bandwidth (estimated), 80 GPU cores
  • M2 Ultra: 192 GB unified, 800 GB/s, 76 GPU cores
  • Metal compute shaders + MLX framework for LLM inference
Apple Silicon's killer advantage: 128-256 GB of GPU-accessible memory at consumer prices. A 70B Q4 model fits in a Mac Studio.
Apple Silicon cannot match discrete GPU bandwidth (546 vs 1008 GB/s for 4090), but the massive unified memory means you can run 70B+ models that simply don't fit on any consumer GPU. This is a unique niche.

Air Cooling

  • Up to ~450W per GPU
  • Simple, well-understood
  • Consumer GPUs, light DC
  • 25-30 kW per rack max

Liquid Cooling

  • 700-1000W+ per GPU
  • Required for H100/B200
  • Cold plates + CDU
  • 60-100 kW per rack

Immersion

  • 1000W+ per GPU
  • Entire server submerged
  • Best thermal uniformity
  • 100-200 kW per rack
NVIDIA's GB200 NVL72 requires liquid cooling - there's no air-cooled option. This means datacenter retrofits for older facilities.

Desktop vs Mac Studio vs Datacenter

Desktop GPU

  • 24-32 GB VRAM
  • High BW (1-1.8 TB/s)
  • 350-575W GPU TDP
  • Models: up to ~32B (Q4)
  • Fast on small models

Mac (Apple Silicon)

  • 64-256 GB unified
  • Moderate BW (400-819 GB/s)
  • 75-150W whole SoC
  • Models: up to ~120B+ (Q4)
  • Silent, power efficient

Datacenter

  • 80-256 GB HBM per GPU
  • Extreme BW (2-8 TB/s)
  • 400-1000W per GPU
  • Models: 405B+ across node
  • Highest throughput
Each tier has a niche: desktop for speed on small models, Mac for large models quietly, datacenter for serving at scale.
The Mac Studio M4 Ultra fills a unique niche - silent, always-on, can run 70B models that no consumer GPU can fit. But at lower speed than a 4090 on models that DO fit in 24GB.

Thermal Throttling and Sustained Performance

  • Junction temperature limit: 83-95C for consumer GPUs, higher for datacenter
  • Throttling reduces clock speed by 15-30% when thermal limit hit
  • LLM inference is a sustained workload - not burst like gaming
  • Consumer GPUs may throttle after 5-10 minutes of continuous inference
  • NVIDIA datacenter GPUs maintain boost clocks indefinitely (with proper cooling)
Real-world LLM tok/s on consumer GPUs can be 10-15% lower than benchmarks due to thermal throttling during sustained use.
If you're running Ollama 24/7 on an RTX 4090, expect sustained performance below peak. Undervolt or increase fan curve for better sustained throughput.

Multi-GPU: NVLink and Infinity Fabric

NVIDIA NVLink

  • NVLink 3 (A100): 600 GB/s bidirectional
  • NVLink 4 (H100): 900 GB/s
  • NVLink 5 (B200): 1800 GB/s
  • NVSwitch: all-to-all GPU fabric

AMD Infinity Fabric

  • MI300X: in-package IF (chiplets)
  • Inter-node: PCIe + xGMI
  • Lower inter-node BW than NVLink
  • But 192GB means less need for multi-GPU
Multi-GPU inference adds latency overhead. 2x GPUs gives ~1.6-1.8x throughput (not 2x) due to communication costs.
Tensor parallelism across GPUs splits the model, but requires synchronization at each layer. The NVLink bandwidth determines how much overhead this adds. PCIe multi-GPU (64 GB/s) is much worse than NVLink.

Key Takeaways

  • Memory bandwidth determines LLM inference speed, not TFLOPS
  • Quantization is the single best lever for local inference (4x speedup for Q4 vs FP16)
  • Consumer GPUs (RTX 4090/5090, RX 7900 XTX) are excellent for 7B-32B models
  • Apple Silicon (M4 Max/Ultra) trades speed for capacity - runs 70B+ at lower tok/s
  • 70B+ at full speed requires datacenter GPUs or multi-GPU setups
  • AMD MI300X offers best memory capacity (192 GB) for single-GPU large models
  • NVIDIA B200's 8 TB/s bandwidth sets a new performance ceiling
  • Chinese alternatives (Huawei, Moore Threads) are 2-3 gens behind but closing fast
The LLM inference landscape is evolving rapidly. Today's datacenter flagship becomes tomorrow's consumer card equivalent in bandwidth. Choose your platform based on model size needs vs speed requirements.
