Tracing & Trace Compass

Context before the code

Before we dive into MCP, let's set the stage. What is tracing, what is Trace Compass, and why did we want to add AI to it?

What is Tracing?

  • Recording timestamped events from a running system, kernel, userspace, network
  • Non-intrusive: nanosecond overhead, always-on capable
  • Produces massive datasets: a few minutes → gigabytes of events
Tracing captures what actually happened in a system at nanosecond granularity. Unlike logging, it's designed for minimal overhead so you can leave it on in production. The downside: it produces enormous volumes of data that are hard to analyze manually.

What is Trace Compass?

  • Open-source Eclipse project for trace visualization & analysis
  • Supports LTTng, CTF, perf, ftrace, and more
  • Powerful, but requires expertise to use effectively
  • Trace Server Protocol (TSP) exposes analysis via REST API
Trace Compass is the Swiss Army knife of trace analysis. It can handle kernel traces, userspace traces, network traces. But the learning curve is steep, you need to know which views to open, which analyses to run, how to interpret the results.

Why Add MCP?

  • Users shouldn't need to be tracing experts to get insights
  • "Find CPU anomalies in this trace" is easier than navigating 20 views
  • AI handles the how, the user focuses on the what

Personal motivation: make trace analysis accessible to everyone, not just the experts who built it

This is the personal motivation. I've spent 16 years building tracing tools, and I've watched users struggle with the complexity. MCP lets us put a natural language interface on top of all that power. Instead of teaching someone Trace Compass, you teach them to ask a question.

What's New in Trace Compass

  • CTF2 support, JSON-based trace metadata, human-readable, AI-parseable
  • Opens the door to smarter AI-driven analysis
  • AI can read trace structure without binary parsing

JSON metadata means AI agents can understand trace schemas natively

CTF2 replaces the binary TSDL metadata with JSON. This is huge for AI integration because LLMs can read and reason about JSON natively. An AI agent could inspect a trace's metadata, understand what events are available, and decide which analyses to run.

TMLL, The ML Layer

  • Anomaly detection, iforest, z-score, IQR, moving average, combined
  • Change point analysis, single, z-score, voting, PCA
  • Correlation analysis, Pearson, Spearman, Kendall
  • Memory leak detection, idle resources, capacity planning

Python ML library on top of the Trace Server Protocol, powerful, but requires code to use

TMLL wraps ML techniques into a clean Python API that talks to the Trace Server. It's the library we're going to make AI-accessible. But until now, users needed to write Python code to use it. That's the gap MCP fills.

What is MCP?

Model Context Protocol, the universal adapter between AI and tools

MCP is an open protocol by Anthropic that standardizes how LLMs interact with external tools. Think of it as USB-C for AI: one connector, every device.

MCP in 30 Seconds

  • Open protocol: JSON-RPC over stdio or HTTP
  • Write a tool once → use from any MCP-compatible agent
  • Adopted by OpenAI, Anthropic, Google, all major IDEs

The key insight: the AI receives tool schemas and decides autonomously which tools to call. The protocol handles the plumbing. The AI handles the reasoning. JSON-RPC keeps it simple and language-agnostic.

Why MCP Matters for You

Deterministic tools + AI reasoning = best of both worlds

This is the practical pitch. Why should you, as a developer, care about MCP?

Deterministic Execution

  • AI decides what to call, your tool decides how to execute
  • No hallucinated analysis, real code runs on real data
  • Reproducible results: same input → same output, every time
The AI picks the right tool and parameters, but the actual computation is your deterministic code. No hallucinated statistics, no made-up numbers.

Save Tokens

  • Don't paste raw data into the prompt, let the tool process it server-side
  • Return summaries, not megabytes of CSV
  • Progressive discovery: only load schemas for tools you actually use (~80% savings)
Without MCP, you'd paste trace data into the prompt and ask the LLM to analyze it. That's expensive, slow, and limited by context window size. With MCP, the heavy lifting happens server-side.

Improve Your Existing Tools

  • Your CLI already works, MCP makes it AI-accessible
  • No rewrite needed: wrap, don't replace
  • Users who can't write Python can now use your tool via natural language

MCP doesn't replace your tools, it gives them a new audience

You don't need to rewrite anything. Wrap your existing CLI as an MCP server, and suddenly every AI assistant in the world can use your tool.

Performance & Cost

Why not just feed the trace to the LLM?

Before we build anything, let's justify the architecture with numbers. Why do we need MCP + TMLL at all, why not just paste the trace into ChatGPT?

Raw Trace → LLM vs MCP + TMLL

ApproachTokensCost (est.)Result
babeltrace → LLM~1B+$1000s per queryHallucinated, non-deterministic
MCP + TMLL~2Kfraction of a centDeterministic ML analysis

A 1 GB kernel trace ≈ billions of text tokens, exceeds every context window

  • LLMs can't reliably do statistics on raw events
  • MCP approach: AI sends one tool call, gets deterministic results back
  • Trace Server + TMLL do the heavy lifting, AI just interprets
This is the key economic argument. A 1 GB trace is billions of tokens, it won't fit in any context window, and even if it did you'd pay thousands of dollars per query and get hallucinated statistics back. With MCP, the AI sends one small tool call and gets a small deterministic answer.

MCP Overhead

OperationDirect TMLL APIMCP (via CLI)
Experiment creation~200 ms~800 ms
Anomaly detection~2 s~3 s
Correlation analysis~1.5 s~2.5 s
  • ~1 s overhead per call (subprocess + Python startup)
  • Negligible next to LLM inference latency
  • Future: in-process mode eliminates the cost
The subprocess wrapper adds about a second per call. That's completely dominated by LLM inference time, so it doesn't matter in practice. If it ever does, we can switch to in-process mode.

Runs Locally, Privacy & Free Compute

  • Trace Compass, TMLL, and the MCP server all run on your machine
  • Your traces never leave the network, critical for regulated, proprietary, or customer data
  • Uses compute you already own, no new cloud bill, no GPU rental
  • The AI only sees the small, aggregated result, not the raw events

We already had the hardware, the server, and the library. MCP just unlocked them.

This is the part that often gets missed. Everything runs locally: the trace server, TMLL, the MCP server. Your trace data, which is often the most sensitive telemetry a company has, never leaves the machine. The AI receives only the distilled result, a few kilobytes of summary. And the compute is free in the sense that it's hardware you already bought and a server you were already running. No new cloud spend, no new data-sharing agreements. We're just putting a natural-language front door on infrastructure that was already there.

How to Start

Step 1: Create a CLI

The recipe is simple. Step 1: if you don't already have a CLI for your tool, write one.

Create a CLI

#!/usr/bin/env python3
"""tmll_cli.py, 12 subcommands wrapping the TMLL library."""
import argparse
from tmll.tmll_client import TMLLClient

def detect_anomalies(args):
    client = TMLLClient(args.host, args.port)
    experiment = get_experiment(client, args.experiment)
    outputs = experiment.find_outputs(keyword=args.keywords, type=['xy'])
    ad = AnomalyDetection(client, experiment, outputs)
    result = ad.find_anomalies(method=args.method)
    print(f"Found {total} anomalies across {len(result.anomalies)} outputs")

# ... 11 more subcommands ...

Standard argparse, nothing MCP-specific yet

This is just a normal Python CLI. argparse, subcommands, print output. Nothing special. Each subcommand maps to one TMLL analysis.

Step 2: Wrap CLI in MCP

~615 lines of Python total

Step 2: wrap each CLI subcommand as an MCP tool using FastMCP. subprocess.run bridges them.

The MCP Wrapper

from mcp.server.fastmcp import FastMCP
mcp = FastMCP("tmll-cli-mcp-server")

@mcp.tool()
def detect_anomalies(experiment_id: str,
                     keywords: list[str] = None,
                     method: str = None) -> str:
    """Detect anomalies in trace data using ML methods."""
    args = build_args({
        "keywords": ("-k", keywords or ["cpu usage"]),
        "method": ("-m", method or "iforest"),
    })
    return run_cli("anomaly", experiment_id, *args)

Any CLI → MCP tool in 5 lines of glue

The @mcp.tool decorator and the docstring tell the AI what the tool does. FastMCP handles schema generation automatically. subprocess.run bridges to the CLI.

The CLI uses argparse with 12 subcommands. The MCP server wraps each CLI command as a tool using FastMCP. This pattern works for any existing CLI tool.

Why MCP → CLI → Library?

  • Separation of concerns, you can access and test your CLI independently, no AI needed
  • MCP is new (2024), put it on tested footing by building on a proven CLI layer
  • One path to maintain, why have two code paths when one works for both humans and AI?
This layering is deliberate. The CLI is your stable, testable interface. MCP is exciting but brand new, first released in 2024. By wrapping the CLI rather than calling the library directly, you get a battle-tested layer underneath. And you avoid maintaining two separate code paths: the CLI works for humans, the MCP wrapper makes it work for AI. Same code, two audiences.

Progressive Discovery

Eager Loading (old)

  • All 12 tool schemas sent upfront
  • ~2,200 tokens consumed before the user says anything

Progressive Discovery (new)

  • Schemas loaded on demand
  • Typical session: 2–3 tools → ~80% savings

FastMCP's progressive discovery means the AI only pays for what it uses

Every tool schema consumes tokens. With progressive discovery, the client only resolves schemas for tools it actually invokes. ~80% fewer tokens spent on tool definitions.

Key Takeaways

  • ~615 lines of Python to make TMLL AI-accessible
  • Pattern: Library → CLI → MCP works for any tool
  • One MCP server → works across Kiro, Gemini, Theia, Goose
  • Progressive discovery saves ~80% of token overhead
  • Runs locally, your traces stay on your machine, on hardware you already own
  • MCP Apps: charts and images inline in AI responses
  • The bottleneck is never the MCP glue, it's the ML analysis and LLM inference
  • Many MCP tools in the wild are sub-optimal, don't judge the technology by a few bad implementations

MCP is a protocol, not a product. The quality is in your hands.

The main message: making your tools AI-accessible via MCP is surprisingly easy. The pattern is general. The ecosystem is ready. And a word of caution: there are a lot of poorly written MCP servers out there. Don't let that colour your view of the protocol itself. A bad REST API doesn't mean HTTP is broken. Same applies here. Build good tools, and MCP will serve you well.
