Performance Impact of Virtualization

The "5% overhead" myth and what the research actually shows

Matthew Khouzam | Ericsson Software Technology | 2026

Everyone says KVM has about 5% overhead. But that number is misleading. The real overhead depends entirely on the workload. We will walk through the research from DORSAL lab at Polytechnique Montreal and Foutse Khomh's group to show what actually happens.

The "5% Overhead" Myth

  • Common claim: "KVM adds about 5% overhead"
  • Based on CPU-bound benchmarks like SPEC CPU - pure compute, no I/O
  • Reality: overhead ranges from under 1% to over 80% depending on workload
  • Syscall-heavy, I/O-heavy, and scheduling-sensitive workloads see dramatically more
A single number cannot describe virtualization overhead. The overhead depends on how the workload interacts with the hardware.
If you run a tight loop doing math, the hypervisor barely touches it. But the moment you start doing syscalls, I/O, or anything that crosses privilege boundaries, the cost spikes. This talk breaks down exactly where and why.

Part 1: The Virtualization Stack

Where does overhead come from?

Before diving into specific overheads, let us understand the layers involved.

The KVM/QEMU Virtualization Stack

Guest Application
Guest OS Kernel (Linux)
KVM (Hypervisor in host kernel)
Host OS Kernel (Linux)
Hardware (VT-x/VT-d, EPT, IOMMU)

Every boundary crossing has a cost. The question is: how often does your workload cross them?

The guest application runs in user mode inside the guest. When it does a syscall, it traps to the guest kernel. When the guest kernel does something the hypervisor must handle (I/O, page faults, privileged instructions), a VM-exit occurs. That VM-exit is where the overhead lives.

The VM-Exit: Root Cause of Overhead

What triggers a VM-Exit

  • I/O port access
  • MSR reads/writes
  • Certain privileged instructions
  • External interrupts
  • EPT violations (page faults)
  • CPUID, HLT, INVLPG

Cost per VM-Exit

  • Save full guest CPU state
  • Restore host CPU state
  • KVM handles the exit reason
  • Restore guest CPU state
  • Resume guest execution
~1-3 microseconds per round-trip on modern hardware
A VM-exit on an Intel Skylake takes roughly 1 to 3 microseconds depending on the exit reason and how much state needs to be saved. That sounds small, but if you are doing 100,000 I/O operations per second, it adds up fast. Benbachir and Dagenais documented these transitions precisely using hypertracing.

Part 2: CPU and Syscall Overhead

Pure compute vs. kernel-intensive workloads

Let us start with the simplest case: CPU-bound work.

CPU-Bound Workloads: Near-Zero Overhead

  • Pure arithmetic in user space runs at native speed
  • VT-x allows guest code to execute directly on the CPU
  • No VM-exits unless the guest touches privileged state
  • SPEC CPU 2017 integer: 0.5-2% overhead
This is where the "5% overhead" number comes from. It is real - but only for this one class of workload.
If your workload is a tight loop doing floating point math, matrix multiplications, or other pure compute, you will see nearly no overhead. The hardware virtualization extensions let the guest run directly on the CPU. This is what vendors benchmark.

Syscall-Heavy Workloads: A Different Story

  • Each syscall in the guest may trigger VM-exits (I/O, page faults, timers)
  • Paravirtualization (virtio, PV clock) reduces but does not eliminate exits
  • High-frequency syscalls: getpid, gettimeofday, read/write on pipes
  • Overhead scales with syscall rate, not CPU utilization
A web server doing 50,000 req/s with 10 syscalls per request = 500,000 potential VM-exit triggers per second.

Benbachir & Dagenais, "Hypertracing: Tracing through virtualization layers," IEEE TCC, 2018

Benbachir and Dagenais showed that you can trace through the hypervisor boundary to see exactly which syscalls cause VM-exits and which are handled without leaving the guest. This gives precise per-syscall overhead measurements.

Part 3: The Double Scheduling Problem

Two schedulers, one CPU, many surprises

Scheduling is where virtualization overhead becomes invisible but devastating.

Two Schedulers, One CPU

Guest Scheduler

  • Sees N vCPUs
  • Schedules guest threads onto vCPUs
  • Thinks it has dedicated CPUs
  • Has no visibility into host decisions

Host Scheduler

  • Sees vCPUs as threads
  • Schedules vCPUs onto pCPUs
  • Can preempt a vCPU at any time
  • Has no visibility into guest priorities
Neither scheduler has full information. The guest may schedule a high-priority task onto a vCPU that the host is about to preempt.
Gebai, Giraldeau, and Dagenais published detailed preemption analysis showing that when the host preempts a vCPU holding a spinlock, every other vCPU waiting on that lock spins uselessly. This is called lock holder preemption and it can cause latency spikes of several milliseconds.

Measuring the Scheduling Gap

  • Lock holder preemption: vCPU preempted while holding a spinlock stalls all waiters
  • NUMA unawareness: guest does not know host NUMA topology, causes remote memory access
  • Timer coalescing: virtual timer interrupts arrive in bursts, distorting latency
  • Mitigation: vCPU pinning, NUMA-aware placement, pause-loop exiting

Gebai, Giraldeau & Dagenais, "Fine-grained preemption analysis for latency investigation across VMs," JCC, 2014

Nemati & Dagenais, "VM processes state detection by hypervisor tracing," SysCon, 2018

Khomh et al., "A Dynamic and Failure-Aware Task Scheduling Framework for Hadoop," IEEE TCC, 2020

Nemati and Dagenais showed that you can reconstruct the full scheduling picture by tracing at the host hypervisor level. You can see exactly when a vCPU is preempted and correlate it with guest-level events. Khomh's group showed that scheduling failures in cloud environments like Hadoop are predictable if you have the right telemetry.

Part 4: Memory Virtualization

Two-level page tables and TLB pressure

Memory is often overlooked but can be a major source of overhead, especially for large working sets.

Extended Page Tables (EPT/NPT)

  • Guest has its own page tables: Guest Virtual to Guest Physical (GVA to GPA)
  • Host adds a second level: Guest Physical to Host Physical (GPA to HPA)
  • Hardware walks both page table levels on a TLB miss
  • A TLB miss in the guest = up to 24 memory accesses (4-level x 4-level + final page)
  • On bare metal, the same miss costs at most 5 memory accesses
EPT/NPT page walks are 4-5x more expensive than native. For workloads with large, sparse memory access patterns, this is devastating.
The nested page walk is the single most expensive per-event overhead in memory virtualization. Each level of the guest page table requires a full walk of the host page table. With 4-level paging on both sides, worst case is 4 times 4 plus 4 memory accesses. Huge pages help because they reduce paging levels.

Memory Overhead Mitigations

TechniqueWhat It DoesTradeoff
Huge Pages (2MB/1GB)Reduces page table depthFragmentation, less flexibility
NUMA PinningKeep guest memory on local nodeHarder live migration
KSM (Kernel Same-page Merging)Deduplicates identical pagesCPU overhead for scanning
Memory BallooningDynamic memory reclaimGuest performance variance

Biancheri & Dagenais, "Fine-grained Multilayer Virtualized Systems Analysis," JCC, 2016

Daoud & Dagenais, "Dynamic trace-based sampling algorithm for memory usage tracking," HPEC, 2017

Biancheri and Dagenais showed that you can trace through multiple virtualization layers simultaneously to see exactly how memory operations cascade through the guest kernel, hypervisor, and host kernel. This multilayer analysis is essential for diagnosing memory performance issues.

Part 5: I/O Performance

Emulated, paravirtualized, and passthrough

I/O is where virtualization overhead hits hardest. Every I/O operation potentially crosses the hypervisor boundary.

Three I/O Approaches

Emulated

QEMU traps every I/O access

VM-exit per operation

30-80% overhead

Paravirtual (virtio)

Shared ring buffers

Batched notifications

5-20% overhead

Passthrough (VFIO)

Direct device access

IOMMU for isolation

0-3% overhead

Belkhiri et al., "Performance analysis of DPDK-based applications through tracing," JPDC, 2023

The choice of I/O strategy dominates the performance picture. Emulated devices are the worst case because QEMU must intercept every single I/O instruction. Virtio is the standard choice and is quite good. VFIO passthrough gives near-native performance but you lose live migration for that device.

Network I/O: The Overhead Spectrum

Typical throughput for 64-byte packets. Higher is better. Based on published benchmarks and DPDK documentation.

Network I/O shows the widest range of overhead. With emulated e1000, you might get 1 Gbps. With virtio-net, 10-15 Gbps. With DPDK and VFIO passthrough, you can reach line rate on a 100G NIC. The choice of I/O backend is far more impactful than the hypervisor itself. Belkhiri and Dagenais showed how to trace DPDK-based applications to identify exactly where the overhead occurs.

VFIO / Device Passthrough

  • IOMMU maps guest physical addresses to host physical for DMA
  • SR-IOV creates multiple Virtual Functions from one physical NIC
  • Guest driver talks directly to hardware - no hypervisor in the data path
  • Interrupts delivered via posted interrupts (no VM-exit)
When to use: Telecom NFV, high-frequency trading, real-time workloads
Tradeoff: No live migration, device tied to one VM, limited scalability
VFIO passthrough is the answer when you need bare-metal I/O performance. For telecom workloads in 5G, this is non-negotiable. But it comes at a cost: you cannot live-migrate a VM with a passed-through device (though some solutions like NVIDIA DOCA and vDPA are working on this).

Part 6: GPU Virtualization

Passthrough, vGPU, and the ML inference question

GPU virtualization is increasingly important as ML workloads move into virtualized environments.

GPU Virtualization Approaches

Passthrough

Entire GPU to one VM

0-2% overhead

No sharing

vGPU (NVIDIA GRID)

Time-sliced sharing

5-15% overhead

Multiple VMs per GPU

API Remoting

Intercept CUDA/OpenCL calls

15-40% overhead

Most flexible

Belkhiri & Dagenais, "Analyzing GPU Performance in Virtualized Environments: A Case Study," Future Internet, 2024

Belkhiri and Dagenais conducted a detailed case study showing that GPU virtualization overhead varies significantly by approach and by workload. Compute-bound GPU kernels see very little overhead with passthrough, while memory-transfer-heavy workloads see more because the DMA path goes through the IOMMU. With API remoting, every CUDA call is intercepted, serialized, and forwarded, which is expensive for fine-grained kernel launches.

GPU Overhead by Workload Type

Relative performance (bare metal = 100%). Based on Belkhiri & Dagenais 2024, Darche & Dagenais 2024.

This chart shows the key insight: compute-heavy GPU workloads see nearly no overhead with passthrough, but memory-transfer-heavy workloads see more because every DMA operation goes through the IOMMU. API remoting adds a constant per-call cost that dominates when you have many small kernel launches. Darche and Dagenais also showed that low-overhead profiling of GPU kernels is possible without significantly impacting performance.

The Big Picture

Overhead depends on the workload, not the hypervisor

Now let us put it all together and see the full range of overhead across workload types.

KVM Overhead by Workload Category

Typical overhead ranges for KVM with standard configurations. Actual values depend on hardware, kernel version, and tuning.

This is the chart that kills the 5% myth. CPU-bound workloads sit at the left end. I/O-intensive workloads with emulated devices sit at the right end. Most real-world workloads are somewhere in between. The key takeaway: you must benchmark YOUR workload, not rely on generic numbers.

Part 7: Cloud Patterns and Energy

Architecture decisions have measurable performance and energy cost

Foutse Khomh's group has done extensive work on how cloud deployment patterns affect performance and energy.

Cloud Patterns Affect Performance

  • Message queuing vs. direct invocation - adds latency, reduces coupling
  • Auto-scaling - improves throughput but cold starts add tail latency
  • Database patterns - CQRS, sharding, caching each have distinct overhead profiles
  • Container orchestration - Kubernetes vs. OpenShift have measurable differences

Khomh et al., "Understanding the impact of cloud patterns on performance and energy consumption," JSS, 2018

Khomh et al., "Kubernetes or OpenShift? Which Technology Best Suits Eclipse Hono IoT Deployments," SOCA, 2018

Khomh and colleagues showed that the choice of cloud patterns has a measurable impact on both performance and energy consumption. For example, message queuing patterns add 10-30ms of latency per hop but improve fault tolerance. The choice of Kubernetes vs OpenShift matters for specific workloads like IoT with Eclipse Hono.

Virtualization and Energy Cost

  • Virtualization overhead = more CPU cycles = more energy per operation
  • Cloud pattern choice can double energy consumption vs. optimal pattern
  • Data-access anti-patterns compound: N+1 queries, missing indexes, unneeded data loading
  • In data centers, 40% of energy goes to cooling - inefficient VMs make this worse

Khomh et al., "A Study of the Energy Consumption of Databases and Cloud Patterns," ICSOC, 2016

Khomh et al., "Data-access performance anti-patterns in data-intensive systems," ESEJ, 2024

Khomh's group demonstrated that cloud patterns significantly affect energy consumption. Anti-patterns in database access compound the problem: an N+1 query pattern inside a virtualized database can consume 10x the energy of a properly batched query. The infrastructure overhead multiplies application-level inefficiency.

Part 8: Measuring Virtualization Overhead

Tracing across the hypervisor boundary

If you cannot measure it, you cannot improve it. DORSAL's core contribution is tools and techniques for measuring virtualization overhead precisely.

Hypertracing: Seeing Through the VM Boundary

  • LTTng in guest and host, correlated by timestamp
  • KVM tracepoints: kvm_entry, kvm_exit, kvm_mmio, kvm_msr
  • Hypertracing: unified trace spanning guest, hypervisor, and host
  • Enables precise attribution: which guest event caused which VM-exit?
Without cross-layer tracing, you see symptoms (slow VM) but not causes (lock holder preemption, EPT violations, I/O traps).

Benbachir & Dagenais, "Hypertracing: Tracing through virtualization layers," IEEE TCC, 2018

Benbachir and Dagenais developed hypertracing, which instruments both guest and host kernels with LTTng and correlates the traces through shared timestamps. This lets you see that a 50ms latency spike in the guest was caused by a specific VM-exit that led to a host page fault. Without this, you are guessing.

Analysis Techniques

What to Measure

  • VM-exit frequency and duration
  • vCPU steal time
  • EPT violation rate
  • Virtio ring buffer occupancy
  • Interrupt delivery latency

Tools

  • LTTng - low-overhead kernel tracing
  • perf kvm - VM-exit profiling
  • eBPF - dynamic probes on KVM
  • Trace Compass - visualization
  • virtFlow - guest-independent analysis

Nemati & Dagenais, "virtFlow: Guest independent execution flow analysis across virtualized environments," IEEE TCC, 2020

Khomh et al., "Tracing Optimization for Performance Modeling and Regression Detection," ACM TOSEM, 2026

Nemati and Dagenais developed virtFlow, which can analyze guest execution flow purely from host-side traces without any instrumentation inside the guest. This is powerful for production environments where you cannot modify the guest. Khomh's recent work on tracing optimization shows how to reduce trace volume while preserving the ability to detect performance regressions. Also see the ICPE 2025 paper on kernel-level event-based performance anomaly detection.

Key Takeaways

What to remember from this talk

Let us wrap up with the main points.

Virtualization Overhead is Not a Number

Workload TypeTypical OverheadDominant Factor
CPU-bound compute0.5-2%Almost none (VT-x)
Memory-intensive5-15%EPT page walks, TLB misses
Scheduling-sensitive10-30%Lock holder preemption, NUMA
Network I/O (virtio)5-20%Virtio overhead, vhost-net
Storage I/O (virtio-blk)5-15%Block layer overhead
Emulated I/O30-80%VM-exit per I/O operation
Benchmark your actual workload. Use tracing to identify which overhead category dominates.
This table is the single most important slide. When someone says KVM has 5% overhead, point them here. The overhead depends on the workload. A database server sees different overhead than a compute cluster. Measure, do not assume.

Practical Recommendations

  1. Use virtio everywhere - never use emulated devices in production
  2. Pin vCPUs to pCPUs - eliminates scheduling jitter
  3. Enable huge pages - reduces EPT walk cost by 4x
  4. NUMA-aware placement - keep memory local to the CPU
  5. VFIO for latency-critical I/O - when you need bare-metal I/O performance
  6. Trace, do not guess - LTTng + Trace Compass shows where time goes
These are the six things you should do for any production KVM deployment. Most of the overhead people complain about comes from not following these practices. Especially points 1 and 2: using emulated devices or not pinning vCPUs accounts for most performance complaints.
